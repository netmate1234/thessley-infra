# Phone-held key Windows sign-in: next prototype boundary

## What the current pilot proves

The current CSR is signed by a non-exportable key created on the Windows PC.
The phone approves the CSR digest, and restricted AD CS issuance can return a
certificate for that PC key. This proves approval binding and certificate
validation; it does not make the phone's key a Windows logon key. Keep the
existing `phone_ephemeral_certificate` policy method disabled.

## Required architecture for a phone-held key

1. **Phone key and enrollment.** The Android app creates a dedicated,
   non-exportable key in Android Keystore; it does not repurpose a website's
   relying-party passkey. The AD service binds its public key to one domain SID
   and verifies fresh key attestation. An enrollment QR proves the phone's
   possession of the private key. The phone, not the PC, creates/signs the CSR.
2. **Restricted certificate issuance.** AD CS issues a Smart Card Logon
   certificate for that phone public key, with the approved account SID and a
   narrowly controlled template. Only the public certificate reaches Windows;
   the private key never does.
3. **Windows cryptographic bridge.** A Windows smart-card minidriver or
   equivalent key provider exposes the phone credential through the supported
   Windows smart-card/Kerberos path. Its private-key signing operation relays
   the exact signing input to the enrolled phone and returns only the
   signature. The Windows Credential Provider gathers the selected SID and
   logon context, then submits the supported Kerberos certificate credential
   serialization. It must not save the account password or copy the phone key.
4. **Phone approval per logon.** Before the phone signs, it shows the machine,
   account, and logon purpose and requires local user verification. Each
   operation is nonce-bound, short-lived, single-use, and protected by the
   pinned service connection. A stale or mismatched request fails closed.
5. **Recovery and rollout.** Keep Windows PIN/password sign-in available during
   the pilot. Enroll and test one disposable domain account first. Enable a new
   policy method only after interactive sign-in, unlock, cancellation, offline,
   and recovery behavior are verified on the VM.

## Concrete protocol boundary

The implemented first slice is account-key enrollment, kept separate from the
current PC-generated CSR flow:

1. The AD service creates a short-lived enrollment challenge bound to the
   account SID, the existing phone-approval credential, and a fresh nonce.
2. Android creates a new P-256 Android Keystore key under a distinct AD-key
   namespace, with user verification required. It returns only the SPKI and
   the attestation chain; it never exports the private key. The app must not
   reuse a website passkey or the phone's existing approval key.
3. The phone proves possession by signing the request with both the existing
   AD approval key and the new key; the pairing code is part of the signed
   request. The service checks account binding, nonce, timestamp, Google-rooted
   attestation/revocation, and duplicate-key policy, then stages the key against
   the immutable SID. It is not active until the administrator confirms the
   matching six-digit code. Enrollment and two-step revocation are auditable.
4. The admin UI displays the verified TEE, StrongBox, software-backed, or
   unverified status. Software-backed keys remain usable but receive a warning.
   The phone polls for administrator confirmation and retains the private key
   only in its separate Android Keystore alias.
5. Certificate issuance from these records is not implemented. The existing
   PC-generated CSR endpoint remains separate and cannot substitute a
   workstation key for the phone key.
6. No enrolled key is a usable Windows credential until the Windows provider
   can route the KDC's private-key signing operation to the phone. That bridge
   and the passwordless sign-in policy remain unimplemented and disabled.

This sequence deliberately keeps three identities distinct: the phone's
existing approval key, the dedicated AD logon key, and any workstation key used
by the current certificate pilot. Each has its own lifecycle and revocation
record. The enrollment endpoint stages a key only after both the existing
central phone key and the new P-256 key sign the same request binding. The
service stores the public key and attestation evidence separately from phone
approval keys, and activates it only after the administrator confirms the
pairing code. The admin account list shows each active key's fingerprint and
attestation status and offers a two-step revoke action. No endpoint issues a
Windows logon certificate from these records or enables sign-in.

The exact UTF-8 signing input is
`thessley_ad_logon_key_enroll_v2|request_id|principal_id|credential_id|public_key_sha256|nonce|timestamp|label|pairing_code`.
The request ID and nonce are generated by the service, the timestamp must be
within its clock-skew window, and the request ID can be stored only once. The
existing approval-key signature authorizes the account binding; the new-key
signature proves possession of the separate private key. The Android client
stores the new alias separately and can retry a request after a dropped
response using the same request ID. Enrollment requires local user verification
for both signing operations. The service verifies supplied Android
attestation against Google roots and its revocation status; unavailable or
invalid evidence is shown as unverified rather than treated as hardware-backed.

## Network dependency

At the Windows sign-in screen, the client must be able to reach the phone or a
relay that can reach the phone. A VPN that requires an interactive browser login
after Windows sign-in cannot provide that path before sign-in. The first pilot
must therefore use a shared local network or a pre-logon-capable network path.
This project targets ordinary physical Windows PCs and network communication
with the phone; USB and NFC are out of scope. It must not silently fall back to
password or a PC-held key.

## Physical Windows PCs: network-only constraint (2026-10-30)

Microsoft's supported Web sign-in provider requires Windows 11 devices joined
to Microsoft Entra ID and internet access; Microsoft explicitly excludes
hybrid-joined and AD-domain-joined devices. Windows Hello for Business cloud
Kerberos trust also requires Microsoft Entra Kerberos and does not support a
pure on-premises AD DS deployment. These are not drop-in routes for this lab.

For pure AD DS and network-only phone communication, the phone's private key
must sign the KDC authentication challenge. A custom smart-card minidriver is
one possible bridge, but it may not be the only one. The candidate below uses
the phone itself as the PKINIT client and asks the Windows Credential Provider
to pass the KDC-issued tickets through the built-in Kerberos authentication
package. This avoids putting a custom key provider in LSA, but remains
unproven for an interactive desktop logon.

The connected A52s LineageOS 24 build was inspected read-only over ADB on
2026-10-30. Its kernel exposes `/dev/ccid_ctrl` and `/dev/ccid_bulk`, but the
phone is not rooted (`su` is unavailable), its current USB mode is `adb`, and
the CCID gadget endpoints are root-owned. This does not provide the required
network-only Windows bridge; no USB-based setup is being pursued.

### Candidate: phone PKINIT plus Windows ticket logon

Microsoft documents that Credential Providers serialize credentials for an
authentication package, and that the Kerberos package accepts
`KERB_TICKET_LOGON` through `LsaLogonUser`. That structure carries the KDC's
host service ticket for `host/<computer>` and optionally a forwarded TGT in a
`KRB_CRED`. Its documentation describes a network logon; it does not establish
that a third-party Credential Provider can use it to create an interactive
desktop session. This is a network-only hypothesis to test, not a promised
login mechanism:

1. Windows starts a single-use request bound to the selected AD SID and this
   computer's host SPN, then displays its QR.
2. After scanning, Android uses the TEE-held key and its AD logon certificate
   to perform PKINIT directly with the domain controller and obtains a TGT.
3. Android requests the host service ticket, packages that ticket and the
   forwarded TGT, and delivers them over the authenticated, machine-bound
   request channel.
4. The Windows Credential Provider tries to serialize `KERB_TICKET_LOGON` for
   the built-in Kerberos package. The experiment must establish whether
   Winlogon/LSA accepts it for `CPUS_LOGON` and creates a usable interactive
   desktop session, not merely a network token or cached ticket.

This was a **candidate, not a verified implementation**. Microsoft describes
`KERB_TICKET_LOGON` as a network logon and separately documents Credential
Provider serialization; it does not document this custom desktop-logon
combination. Clone 1 testing now covers both pointer forms at direct LSA and
the actual Credential Provider path:

- Direct `LsaLogonUser(Interactive, KerbTicketLogon)` accepted a native
  in-buffer pointer and returned a primary token; the same structure with a
  raw `0x20` offset returned `STATUS_INVALID_PARAMETER`.
- The offset-based Credential Provider returned
  `STATUS_INVALID_PARAMETER` (`0xC000000D`) through LogonUI.
- A separate provider build using a native pointer reached `ReportResult` but
  returned `STATUS_LOGON_FAILURE` / `STATUS_INTERNAL_ERROR`
  (`0xC000006D` / `0xC00000E5`). It did not create a desktop session.

The direct probe and provider attempts used separate tickets for the same
account and HOST SPN; the ticket bytes were not compared or logged. The native
pointer error is consistent with the provider's address not being valid in the
process that calls LSA, but the status alone does not prove Winlogon's exact
copy/rebase behavior. No supported `KERB_TICKET_LOGON` packing contract for a
Credential Provider was found. Do not repeat this experiment or start phone
PKINIT work on top of this handoff unless a new documented or demonstrated
Winlogon representation is identified. Even a successful run of this
harness would require a password-seeded HOST ticket for each computer and
would therefore miss the product requirement.

The ticket route is not a working path. Keep all existing recovery providers
available and keep phone-key certificate issuance/sign-in disabled. The next
technical route to evaluate is the documented Kerberos certificate/smart-card
logon path with a phone signing bridge; its production signing and cost
requirements remain unresolved.

Microsoft's [KERB_TICKET_LOGON documentation](https://learn.microsoft.com/en-us/windows/win32/api/ntsecapi/ns-ntsecapi-kerb_ticket_logon)
explicitly describes a network-logon structure. The [LsaLogonUser
documentation](https://learn.microsoft.com/en-us/windows/win32/api/ntsecapi/nf-ntsecapi-lsalogonuser)
distinguishes it from `KERB_INTERACTIVE_LOGON`, which is documented for
interactive authentication. That distinction is why the Clone 1 test must
verify an actual desktop session, not infer one from a valid ticket or token.

This means the **temporary Clone 1 harness** needs a normal logon for that
user on that PC to seed a three-minute ticket cache. It would need this on
each PC after cache loss or expiry. That is a limitation of the harness, not
a requirement of the intended QR design, and the harness must not be presented
as a usable passwordless sign-in implementation. Do not ask for repeated
password/PIN logons just to produce another cache-miss result.

An earlier proposal had the phone use its enrolled, non-exportable key for
PKINIT directly with the domain controller and deliver tickets to the PC for
`KERB_TICKET_LOGON`. The subsequent Clone 1 Credential Provider tests rejected
both tested pointer representations, so that proposal is superseded and must
not be treated as an implementation plan. Kerberos PKINIT remains the
standard public-key initial-authentication exchange, but the Windows handoff
for this design is unresolved.

Apache Kerby was inspected as a possible Java client and is **not suitable as
a drop-in PKINIT implementation** in its current source state. Its identity
parser recognizes `PKCS11:` but leaves PKCS#11 parsing and certificate loading
as TODO/empty methods; the PKINIT request path's `signAuthPack()` wraps the
AuthPack but does not call the separate helper that creates CMS signed data.
Using Kerby would require completing and maintaining those security-critical
paths before it could be evaluated with Android Keystore.

MIT krb5 is a more credible implementation base to prototype: its PKINIT
configuration accepts a `PKCS11:` identity and its PKINIT crypto plugin has a
PKCS#11 signing path. A possible Android design is MIT krb5 for the protocol
plus a small custom PKCS#11 module that exposes the phone certificate and
forwards private-key signing to Android Keystore through JNI. This keeps the
private key non-exportable, but is only a candidate: building and integrating
the library for Android, bridging UI-bound key authorization safely, and
proving interoperability with this AD CS/KDC setup remain open work. See the
[MIT krb5 PKINIT identity configuration](https://github.com/krb5/krb5/blob/master/doc/admin/conf_files/krb5_conf.rst)
and [MIT PKINIT PKCS#11 signing implementation](https://github.com/krb5/krb5/blob/master/src/plugins/preauth/pkinit/pkinit_crypto_openssl.c).

Do not prototype phone-side PKINIT until a supported Windows handoff is
identified and demonstrated to create a real `CPUS_LOGON` desktop session.
The ticket experiment is paused at the Windows handoff boundary; the phone's
TEE key and certificate must not be enabled as a Windows logon credential
until that bridge is proven.

## Compatibility questions for the Windows bridge

- Can the Android hardware-backed key algorithm be accepted by the chosen AD
  CS template, Windows smart-card provider, and domain controller PKINIT path?
- Can the Windows minidriver/provider call the phone safely from the LogonUI
  security context, and what supported transport works before logon?
- Which Windows versions and editions support the required provider contract?
- How are certificate renewal, phone revocation, lost-phone recovery, and
  certificate revocation reflected at every workstation?

These questions need a disposable VM and CA. The current PC-key certificate
pilot is useful for validating the issuer and SID/template checks, but it does
not answer them. Do not wire it to the existing TPM VSC serializer or enable it
as a sign-in policy.

## Microsoft contracts

- [`KERB_CERTIFICATE_LOGON`](https://learn.microsoft.com/en-us/windows/win32/api/ntsecapi/ns-ntsecapi-kerb_certificate_logon) describes the Kerberos smart-card logon serialization.
- [`KERB_SMARTCARD_CSP_INFO`](https://learn.microsoft.com/en-us/windows/win32/secauthn/kerb-smartcard-csp-info) describes the provider, container, card, and reader metadata passed with it.
- [Smart Card Architecture](https://learn.microsoft.com/en-us/windows/security/identity-protection/smart-cards/smart-card-architecture) describes the Windows credential-provider and Base CSP/KSP/minidriver layers.
- [Smart Card Minidriver Overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/smartcard/smart-card-minidriver-overview) describes the card-specific interface a provider implementation must satisfy.

## Windows bridge feasibility gate

The Windows signing bridge is the remaining platform blocker, not CSR creation.
The smart-card minidriver is a DLL below the Base CSP/KSP and is called through
the Windows Smart Card Resource Manager. Microsoft documents that a plug-in
loaded into a protected LSA process must carry a Microsoft signature; its
examples explicitly include smart-card drivers and cryptographic plug-ins.
Microsoft also points to the Windows Hardware Compatibility Program as the
method for obtaining that driver signature. See [Smart Card Minidriver
Overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/smartcard/smart-card-minidriver-overview).

### QR-only phone-key research route

The QR carries only a short-lived, single-use request locator and challenge;
it never contains a private key or a reusable credential. The phone app uses
the separately enrolled Android Keystore key. There is no NFC path. The
Android app and DC implement admin-started key enrollment and code
confirmation. On 2026-10-30, the active `THESSLEYLAB\Administrator` key was
confirmed as `verified_tee`. The phone generated a 223-byte DER PKCS#10 CSR;
its ECDSA signature verified, and its SPKI SHA-256 matched the active key in
the DC registry. This proves that the exported CSR uses that enrolled phone
key while the private key remains in Android Keystore.

The CSR exposed a service validation bug: the validator required at least 256
DER bytes and a randomized Windows-pilot subject, while this valid P-256 phone
CSR is 223 bytes and uses `CN=Thessley AD Logon Key`. The fix accepts that exact
EC profile and requires its SPKI digest to match an active AD key for the
approved SID at upload, issuer claim, and certificate acceptance. On
2026-10-30, the fix was deployed to `THESSLEY-DC1`; the installed Python
validator accepted the Android CSR, verified its signature, and confirmed its
SPKI hash matched an active key for the tested SID. This was a read-only
validation; it did not claim an issuance job or contact AD CS.

At the time of the phone-key CSR validation, no certificate had been issued.
The live service configuration still has `certificate_template` unset and
phone-key sign-in remains disabled. A later, separate Software KSP experiment
issued a four-hour certificate for the disposable `startmenutest` identity;
it used a PC-generated key and did not involve the phone key. See the Clone 1
probe results below. Do not use the privileged `THESSLEYLAB\Administrator`
account for certificate experiments. `THESSLEYLAB\qrtestadmin` is enabled
and belongs to the workstation-admin group, but has no active AD logon key.
It is not a Domain Admin, but still has elevated rights on enrolled
workstations. A certificate by itself does not provide a phone-signing bridge
for Windows sign-in.

The next proof must bind a fresh Windows sign-in challenge to the QR request,
have the phone sign it after biometric approval, and demonstrate that the
Windows Kerberos authentication path can consume that signature. A CSR or QR
approval alone cannot do this. Do not label either as phone-key Windows sign-in.

Without budget for Microsoft signing, keep the working Windows route as QR
approval followed by the existing TPM virtual smart-card key while the phone
certificate flow is proved separately. That retains the current UX but has a
different key location: the private logon key stays in the PC TPM. A genuine
phone-held Windows logon still requires a supported way for the Windows
authentication path to request and receive the phone's signature.

### Why the custom provider route is deferred

Microsoft says protected LSA plug-ins need a Microsoft signature, and smart
card drivers require WHQL signing. Disabling LSA protection just to load an
unsigned Thessley minidriver is not an acceptable installation default. There
is a second constraint on a custom CNG KSP route: Microsoft's [Key Storage and
Retrieval](https://learn.microsoft.com/en-us/windows/desktop/SecCNG/key-storage-and-retrieval)
documentation says third-party KSPs are not loaded in the key-isolation
service. Since Windows certificate logon needs the system authentication path
to reach the signing key, we must not assume a custom remote KSP can be called
from that path. This is an architectural inference from Microsoft's provider
and key-isolation descriptions; it needs an isolated Windows proof before it
can be treated as a supported route. A Credential Provider alone cannot make
the certificate private key available to Kerberos.

Do not issue or install a phone-key certificate as if it were a usable Windows
credential before one route has passed the bridge gate. A certificate only
contains the public key; it does not make Windows able to ask Android Keystore
to sign the Kerberos challenge. The enrollment registry records Google-rooted
attestation as verified TEE, StrongBox, software-backed, or unverified, but
that status describes key protection only; it does not authorize a Windows
logon. Keep the certificate issuer and Windows sign-in policy disabled until
the phone-signing bridge is implemented and reviewed.

The lab provider's SID and TPM container values are now read from protected
per-account configuration; they remain TPM VSC test mappings, not phone-key
credentials or product defaults. Keep that provider isolated under
`windows-logon-provider/`.

derived Subject Key Identifier, AD CS wraps the SID `OtherName` in the
GeneralNames context tag and encodes the SID text in its OCTET STRING, and
`cryptography` decodes the template extension as `MSCertificateTemplate`.
The validators now accept those exact formats while rejecting other CSR
extensions and unexpected SID wrappers.

The certificate was installed with its matching non-exportable machine key
under `Microsoft Software Key Storage Provider`. The isolated
`certificate_logon_probe.exe` ran as LocalSystem and called
`LsaLogonUser(KerbCertificateLogon)` for `startmenutest`. All three attempts
returned `lsa_logon_user=0xC000006D` and `lsa_substatus=0xC0000384`
(`STATUS_SMARTCARD_NO_KEY_CONTAINER`): KeySpec 1 and 2 with the generated
container name, and KeySpec 1 with the KSP unique name. No token was returned.
The DC Security log query found no matching 4768 event. This is evidence that
the software-KSP key did not get used by this smart-card logon path; it does
not establish that every certificate-based phone-approval architecture is a
dead end. Microsoft's `KERB_SMARTCARD_CSP_INFO` contract explicitly describes
smart-card CSP data, so the next useful comparison is a disposable key in a
legacy CryptoAPI CSP or the already-working PIV path—not more variations of
the same KSP container string. See Microsoft's [CSP info structure]
(https://learn.microsoft.com/en-us/windows/win32/secauthn/kerb-smartcard-csp-info)
and [smart-card sign-in flow]
(https://learn.microsoft.com/en-us/windows/security/identity-protection/smart-cards/smart-card-certificate-requirements-and-enumeration).

Cleanup completed: the certificate was revoked on the CA with reason
Certificate Hold, a fresh CRL was published, and the Clone 1 certificate,
machine key, CSR, manifest, and probe files were removed. The pilot template
was unpublished and its direct Enroll grant removed. Its CA database issuance
and revocation records remain as an audit trail; the certificate expires four
hours after issuance.

### Clone 1 legacy CryptoAPI CSP comparison (2026-10-30)

To distinguish a KSP-specific lookup failure from the legacy smart-card CSP
path described by `KERB_SMARTCARD_CSP_INFO`, the unpublished four-hour pilot
template was temporarily configured for the version-4 legacy-provider path:
`pKIDefaultKeySpec=1`,
`pKIDefaultCSPs="1,Microsoft Enhanced RSA and AES Cryptographic Provider"`,
and `CT_FLAG_USE_LEGACY_PROVIDER` in `msPKI-Private-Key-Flag`. It was
published only while `THESSLEYLAB\startmenutest` had the direct Enroll right.
The shared `SmartcardLogon` template was not changed.

Clone 1 generated a non-exportable 3072-bit machine key in the Microsoft
Enhanced RSA and AES CryptoAPI provider (`ProviderType=24`, `AT_KEYEXCHANGE`)
and submitted its CSR as `startmenutest`. The CA issued two four-hour
certificates for the same low-privilege test account after the scheduled
request task was started twice. The unused certificate was revoked with
Certificate Hold before probing. The remaining certificate was checked for
the expected `startmenutest` SID extension, Smart Card Logon EKU, pilot
template OID, direct CA issuer, and four-hour validity, then linked to the
non-exportable machine key with `certreq -accept`.

The SYSTEM LSA probe used that provider, container, and `AT_KEYEXCHANGE`.
`LsaLogonUser(KerbCertificateLogon)` returned
`STATUS_LOGON_FAILURE` (`0xC000006D`) with
`STATUS_SMARTCARD_SUBSYSTEM_FAILURE` (`0xC0000321`) as its substatus. This is
different from the KSP test's `STATUS_SMARTCARD_NO_KEY_CONTAINER`. Microsoft's
NTSTATUS reference describes `STATUS_SMARTCARD_SUBSYSTEM_FAILURE` as an error
while Kerberos was attempting to use the smart-card subsystem
([MS-ERREF](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55)).
The probe returned no token and the DC Security log had no matching 4768
event, so this direct LSA call did not complete domain PKINIT. It does not
prove a phone-backed smart-card provider cannot work; it shows that the
generic software CryptoAPI key alone does not complete the logon. Further
KSP container-name permutations are not useful. The remaining implementation
work is on a real smart-card-provider path that can relay signing to the
phone.

Cleanup revoked the probed certificate with Certificate Hold and published a
fresh CRL. Both issued probe certificates are recorded as revoked in the CA
database. The local certificate, all `ThessleyCspProbe-*` key containers,
temporary CSR/certificate files, and scheduled probe tasks were removed and
verified absent. The pilot template was unpublished, its direct Enroll right
for `startmenutest` was removed, and its cryptography fields were restored to
their original CNG values. The template object remains in AD, unpublished;
the shared template remains unchanged.

### Clone 1 ECC sign-in policy preparation (2026-10-30)

The existing phone AD logon key is P-256 ECDSA. Microsoft documents two
separate computer policies that affect whether its certificate can be used at
the sign-in screen: `EnumerateECCCerts` enables ECC certificate enumeration,
and `AllowSignatureOnlyKeys` enables signature-only certificates to appear.
Both were absent on Clone 1. The Microsoft policy reference says both are
computer settings and do not require restart or sign-out
([Smart Card Group Policy and Registry Settings](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-R2-and-2012/dn579258(v=ws.11))).

On the disposable Clone 1 only, both were set to DWORD `1` under
`HKLM\SOFTWARE\Policies\Microsoft\Windows\SmartCardCredentialProvider`.
Read-back confirmed both values. This only permits Windows to enumerate ECC
and signature-only smart-card certificates; it does not enroll a certificate,
create a key, enable the Thessley tile, or remove password recovery. To undo
this lab preparation, delete those two values:

```cmd
reg delete HKLM\SOFTWARE\Policies\Microsoft\Windows\SmartCardCredentialProvider /v EnumerateECCCerts /f
reg delete HKLM\SOFTWARE\Policies\Microsoft\Windows\SmartCardCredentialProvider /v AllowSignatureOnlyKeys /f
```

Authentication EKUs, AD-derived subject, UPN SAN, and SID security extension.

### Disposable virtual-reader discovery POC (2026-10-30)

The Clone 1 experiment uses a loopback-only vpcd client and a disposable PIV
card responder. It does not change the physical phone, the phone's secure
element/TEE, or any enrolled key. It reads the already-issued public
`startmenutest` certificate from the VM's `.cer` file; it has no private key
and does not communicate with the phone to sign.

The responder advertises the full versioned PIV AID and exposes the
certificate only in PIV Authentication object `5FC105`. It accepts only the
test PIN `0000` and deliberately refuses GENERAL AUTHENTICATE (`6A81`). Its
log contains APDU names and lengths, but does not log the PIN value. It is a
diagnostic harness, not a usable smart card or login mechanism.

Observed on Clone 1: Windows selected the PIV AID, fetched CHUID (`5FC102`),
and in one enumeration fetched all 2,243 bytes of the certificate object
(`5FC105`) using GET RESPONSE chaining. Windows also queried several optional
objects, which the responder correctly reported absent. A later scan read
only CHUID and reset the card. No VERIFY or GENERAL AUTHENTICATE was observed
in the latest trace. `certutil -scinfo` reported `NTE_BAD_KEYSET` / “Missing
stored keyset” for the virtual PIV card and did not enumerate the phone-bound
certificate as a usable sign-in certificate. The user-facing smart-card
message was “No valid certificates were found on this smartcard.”

This establishes that the UMDF reader, PC/SC path, PIV AID selection, and
certificate-object transport can work. It does **not** establish that Windows
accepts the returned object as a usable certificate/key pair, that Windows
requested a phone signature, that PKINIT reached the DC, or that AD login
works. The unchanged physical phone is not the card presented by this VM
POC. Microsoft's documented sign-in enumeration first opens the card's
default crypto container; if that fails, Windows considers the card unusable.
It then obtains certificates from the provider's user certificate store or
from the container's `AT_KEYEXCHANGE` certificate. The POC deliberately has
no private-key container and rejects signing, so `NTE_BAD_KEYSET` is expected
and explains why the certificate is not offered as a usable logon credential.
This is a missing bridge implementation, not a change to or failure of the
phone's secure chip. See Microsoft's [certificate enumeration and sign-in
flow](https://learn.microsoft.com/en-us/windows/security/identity-protection/smart-cards/smart-card-certificate-requirements-and-enumeration).

The next implementation step is to connect PIV key reference `9A` and its
ECDSA operation to the existing phone TEE key, with a fresh, account- and
computer-bound phone approval before the signature is returned. The card
provider must then expose the certificate and key as one usable container.
Only after Windows requests the signature can a matching DC PKINIT event and
a successful Windows session establish end-to-end login.
