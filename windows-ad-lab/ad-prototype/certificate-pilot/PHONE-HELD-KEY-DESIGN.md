# Phone-held key Windows sign-in: next prototype boundary

## What the current pilot proves

The current CSR is signed by a non-exportable key created on the Windows PC.
The phone approves the CSR digest, and restricted AD CS issuance can return a
certificate for that PC key. This proves approval binding and certificate
validation; it does not make the phone's key a Windows logon key. Keep the
existing `phone_ephemeral_certificate` policy method disabled.

## Required architecture for a phone-held key

1. **Phone key and enrollment.** The Android app creates a dedicated,
   non-exportable key in Android Keystore; it does not repurpose a website's
   relying-party passkey. The AD service binds its public key to one domain SID
   and verifies fresh key attestation. An enrollment QR proves the phone's
   possession of the private key. The phone, not the PC, creates/signs the CSR.
2. **Restricted certificate issuance.** AD CS issues a Smart Card Logon
   certificate for that phone public key, with the approved account SID and a
   narrowly controlled template. Only the public certificate reaches Windows;
   the private key never does.
3. **Windows cryptographic bridge.** A Windows smart-card minidriver or
   equivalent key provider exposes the phone credential through the supported
   Windows smart-card/Kerberos path. Its private-key signing operation relays
   the exact signing input to the enrolled phone and returns only the
   signature. The Windows Credential Provider gathers the selected SID and
   logon context, then submits the supported Kerberos certificate credential
   serialization. It must not save the account password or copy the phone key.
4. **Phone approval per logon.** Before the phone signs, it shows the machine,
   account, and logon purpose and requires local user verification. Each
   operation is nonce-bound, short-lived, single-use, and protected by the
   pinned service connection. A stale or mismatched request fails closed.
5. **Recovery and rollout.** Keep Windows PIN/password sign-in available during
   the pilot. Enroll and test one disposable domain account first. Enable a new
   policy method only after interactive sign-in, unlock, cancellation, offline,
   and recovery behavior are verified on the VM.

## Concrete protocol boundary

The first implementation slice should be account-key enrollment, kept separate
from the current PC-generated CSR flow:

1. The AD service creates a short-lived enrollment challenge bound to the
   account SID, the existing phone-approval credential, and a fresh nonce.
2. Android creates a new P-256 Android Keystore key under a distinct AD-key
   namespace, with user verification required. It returns only the SPKI and
   the attestation chain; it never exports the private key. The app must not
   reuse a website passkey or the phone's existing approval key.
3. The phone proves possession by signing the challenge. The AD service checks
   the signature, account binding, nonce, attestation policy, and duplicate-key
   policy before recording the key against the immutable SID. Enrollment and
   revocation are auditable and independently available to administrators.
4. Certificate issuance consumes that recorded public key and the SID. The
   phone creates the CSR; the PC-generated CSR endpoint remains separate and
   cannot silently substitute a workstation key.
5. The certificate is not a usable Windows credential until the Windows
   provider can route the KDC's private-key signing operation to the phone.
   Until that bridge exists and is verified, the login policy remains disabled.

This sequence deliberately keeps three identities distinct: the phone's
existing approval key, the dedicated AD logon key, and any workstation key used
by the current certificate pilot. Each needs its own lifecycle and revocation
record. The first server slice accepts
`POST /thessley-ad/v1/logon-keys/enroll` only when both the existing central
phone key and the new P-256 key sign the same request binding (principal ID,
credential ID, SPKI digest, nonce, timestamp, request ID, and label). It stores
the public key and attestation chain separately from phone approval keys.
Attestation remains `unverified`; no endpoint can issue a certificate from
these records or enable sign-in. The AD admin page lists each recorded key by
label, fingerprint, and attestation state, and offers a two-step revoke action.

The exact UTF-8 signing input is
`thessley_ad_logon_key_enroll_v1|request_id|principal_id|credential_id|public_key_sha256|nonce|timestamp|label`.
The request ID and nonce are generated by the phone, the timestamp must be
within the service's existing clock-skew window, and the request ID can be
stored only once. The existing approval-key signature authorizes the account
binding; the new-key signature proves possession of the separate private key.
The Android client stores the new alias separately and can retry a request
after a dropped response using the same request ID. Registration asks for
biometric authorization by both the existing approval key and the new key.
Attestation evidence may be empty on devices that do not provide a chain; such
keys still remain unverified and unusable for sign-in.

## Network dependency

At the Windows sign-in screen, the client must be able to reach the phone or a
relay that can reach the phone. A VPN that requires an interactive browser login
after Windows sign-in cannot provide that path before sign-in. The first pilot
must therefore use either a shared local network, a pre-logon-capable network
path, or a deliberately designed USB transport. The design must state which
one it supports; it must not silently fall back to password or a PC-held key.

## Compatibility questions before implementation

- Can the Android hardware-backed key algorithm be accepted by the chosen AD
  CS template, Windows smart-card provider, and domain controller PKINIT path?
- Can the Windows minidriver/provider call the phone safely from the LogonUI
  security context, and what supported transport works before logon?
- Which Windows versions and editions support the required provider contract?
- How are certificate renewal, phone revocation, lost-phone recovery, and
  certificate revocation reflected at every workstation?

These questions need a disposable VM and CA. The current PC-key certificate
pilot is useful for validating the issuer and SID/template checks, but it does
not answer them. Do not wire it to the existing TPM VSC serializer or enable it
as a sign-in policy.

## Microsoft contracts

- [`KERB_CERTIFICATE_LOGON`](https://learn.microsoft.com/en-us/windows/win32/api/ntsecapi/ns-ntsecapi-kerb_certificate_logon) describes the Kerberos smart-card logon serialization.
- [`KERB_SMARTCARD_CSP_INFO`](https://learn.microsoft.com/en-us/windows/win32/secauthn/kerb-smartcard-csp-info) describes the provider, container, card, and reader metadata passed with it.
- [Smart Card Architecture](https://learn.microsoft.com/en-us/windows/security/identity-protection/smart-cards/smart-card-architecture) describes the Windows credential-provider and Base CSP/KSP/minidriver layers.
- [Smart Card Minidriver Overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/smartcard/smart-card-minidriver-overview) describes the card-specific interface a provider implementation must satisfy.

## Windows bridge feasibility gate

The Windows signing bridge is the remaining platform blocker, not CSR creation.
The smart-card minidriver is a DLL below the Base CSP/KSP and is called through
the Windows Smart Card Resource Manager. Microsoft documents that a plug-in
loaded into a protected LSA process must carry a Microsoft signature; its
examples explicitly include smart-card drivers and cryptographic plug-ins.
Microsoft also points to the Windows Hardware Compatibility Program as the
method for obtaining that driver signature. See [Smart Card Minidriver
Overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/smartcard/smart-card-minidriver-overview).

That means a locally built Thessley minidriver is not yet a deployable bridge
for normal machines with LSA protection. Disabling LSA protection just to load
an unsigned prototype is not an acceptable installation default. Before
building a real bridge, select and prove one of these routes on a disposable
VM:

1. A Microsoft-signable smart-card minidriver backed by a supported device
   transport. The Windows smart-card stack must be able to enumerate the
   phone key and request its signature through that transport.
2. A documented, supported Windows key-provider integration that can broker
   the signature without putting an unsigned plug-in in protected LSA. This
   route still needs a pre-logon transport and a provider lifecycle that
   survives lock, unlock, cancellation, and network loss.
3. If neither is available, keep the production behavior as phone approval
   followed by the existing TPM virtual smart-card key. That is a different
   security model: the private key is on the PC, and the phone approves each
   use.

There is a second constraint on a custom CNG KSP route: Microsoft's [Key
Storage and Retrieval](https://learn.microsoft.com/en-us/windows/desktop/SecCNG/key-storage-and-retrieval)
documentation says third-party KSPs are not loaded in the key-isolation
service. Since Windows certificate logon needs the system authentication path
to reach the signing key, we must not assume a custom remote KSP can be called
from that path. This is an architectural inference from Microsoft's provider
and key-isolation descriptions; it needs an isolated Windows proof before it
can be treated as a supported route. A Credential Provider alone cannot make
the certificate private key available to Kerberos.

Do not issue or install a phone-key certificate as if it were a usable Windows
credential before one route has passed the bridge gate. A certificate only
contains the public key; it does not make Windows able to ask Android Keystore
to sign the Kerberos challenge. The enrollment registry therefore continues
to label phone-key attestation `unverified`, and `active_public_key()` only
returns keys after a separate verifier has marked them verified. Keep the
certificate issuer and the Windows sign-in policy disabled until both the
attestation verifier and signing bridge are implemented and reviewed.

The lab provider's current SID and TPM container values are test fixtures, not
product defaults. Keep them isolated under `windows-logon-provider/`; do not
copy them into the general installer or use them to identify users. A future
general provider must resolve the selected account by immutable SID and obtain
its certificate/key-container mapping from protected machine configuration or
the Windows certificate/card enumeration APIs, with no compiled-in lab SID,
domain name, or container name.
